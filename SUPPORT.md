# Support and request routing

Choose the narrowest public or private channel that fits the request. Each
repository may override this document with more specific instructions.

| Need | Where to go |
| --- | --- |
| Reproducible defect | Open a bug report in the affected repository |
| Product or technical improvement | Open a feature proposal in the affected repository |
| Documentation correction | Open an issue or a focused pull request |
| Usage question | Read the repository documentation, then use its enabled discussion or support channel |
| Suspected vulnerability | Follow [`SECURITY.md`](SECURITY.md) and report privately |
| Conduct concern | Follow [`CODE_OF_CONDUCT.md`](CODE_OF_CONDUCT.md) and report privately |

## Before opening an issue

- Check the repository's README, documentation, status, and supported
  environments.
- Search open and closed issues for the same problem.
- Reduce the problem to the smallest safe reproduction you can provide.
- Remove credentials, personal data, private URLs, customer information, and
  proprietary files.
- Use the issue form fields instead of replacing them with an unstructured
  description.

## Scope and response times

Public repositories are maintained according to the status stated in their
README. An experimental project may change without notice, while an archived
project may accept no new work.

Opening an issue does not create a service-level agreement or guarantee that a
request will be implemented. Clear reproduction steps, concrete outcomes, and
a willingness to help make a request easier to assess.

GitHub issues are public. If a request cannot be discussed safely in public,
do not post sensitive details while asking for a private contact route.
